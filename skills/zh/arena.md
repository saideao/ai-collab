# arena（多模型竞技场与嫁接）

> **简介**：派 N 个并行候选模型完成同一个任务，先定评分标准，再挑一版当底子，把落选版本里最强的部分手工嫁接进去。适合一次尝试就容易把方向定死的非简单任务。

启动任何工作前，先建一份待办清单，每个阶段一条（Frame、Fan out、Cross-judge、Pick、Graft、Verify）。

## 阶段 A：出题与定标准（Frame）

每个参赛者拿到的是同一份提示词，所以提示词就是合同。

1. 明确每个候选者需要产出的具体成品是什么。
2. 制定评分表（rubric）：3 到 6 条针对*当前*任务、具体可打分的标准。这是阶段 D 评选者的工具，参赛者只能看到任务本身，看不到评分表。
3. 从 `~/.cursor/rules/pstack-models.mdc` 的 `arena runners` 行选择参赛模型，默认是 `claude-fable-5-2-high`、`claude-opus-5-5-high-fast` 和 `gemini-4-neon-xhigh`。若配置为 `auto` 或 `inherit-parent`，则沿用父模型。若工具拒绝某个模型名，换同家族最近的有效模型或减少席位，至少保留两个参赛者并说明情况。按 **poteto-mode** 的子助手规则设置推理强度。
4. 为每个候选者分配独立的输出位置（优先使用独立的 git worktree，否则用 `/tmp/arena-<slug>/candidate-<n>/`），遵循 **separate-before-serializing-shared-state** 原则。

## 阶段 B：并行开跑（Fan out）

在一条消息里并行启动全部 N 个后台子助手（`run_in_background: true`），给每个助手发相同的任务、共享背景路径、各自的输出路径，并要求它们交付成品外加一段简短说明：考虑过哪些备选方案、为什么否决了它们。

如果有候选者没产出结果，继续推进剩余的 N-1 份并注明缺席情况。

## 阶段 C：跨厂商裁判（Cross-judge）

全部候选者完成后，从 `arena cross-judge pool` 池里启动一名只读裁判（默认 `claude-opus-5-5-high-fast`、`gemini-4-neon-xhigh`）。**裁判绝不能和主控 AI 来自同一家厂商**（Fable 算 Claude 家族），因此选用池中第一个来自其他厂商的模型。在你进行阶段 D 阅读的同时，裁判按路径编号对每份候选逐条照评分表打分，并推荐一个底子。

## 阶段 D：挑一个底子（Pick a base）

挑选前把每一份候选从头读到尾。逐条对照评分表打分，不要凭整体感觉，并与阶段 C 裁判的结果对比。两边挑的一致，就确认人选；不一致，说明其中一方有偏见或者评分表本身含糊，把两边的理由都读完再定夺。

挑选未来维护者最容易扩展且不会破坏不变量的那一版当底子。如果两版不相上下，按懒惰协议（Laziness Protocol）选边界更干净、接口更小的那一版。

## 阶段 E：手工嫁接（Graft）

把每份落选候选再过一遍，挑出值得移植进底子的好东西——每份通常只取一两处，不要大段照搬。遵循 **redesign-from-first-principles** 原则，手工把每一处优点揉进底子里，保持整份作品在同一个心智模型下连贯完整，绝不要机械粘贴。

如果几份候选不约而同收敛到同一个形状，说明方向非常稳，直接注明共识并采用，不需要嫁接。如果它们差得离谱，说明阶段 A 的题目没出清楚——**回去重新框定题目再跑一遍，不要把分歧平均掉。**

## 阶段 F：验证（Verify）

遵循 **prove-it-works** 原则，像验证其他任何产物一样验证综合后的最终成品。如果验证查出了竞技场漏掉的问题，要么是阶段 A 题目错了（重新框定重跑），要么是某个候选抓到了但你漏嫁接了（回到阶段 E）。不要掩饰过去。

## 最终输出（Outputs）

一份综合后的成品，附一份简短综合说明：选了哪版当底子及理由、跨厂商裁判的结论（或说明跳过了裁判）、每一处嫁接来自哪份候选、哪些被拒绝及原因、是否出现收敛或中途缺席，以及最终验证结果。

# recall（开工前把上下文找回来）

> **简介**：从你自己的聊天记录、当前实时状态以及公共记录（用户反馈、历史修复、线上报错）中重建近期工作上下文，交回一份紧凑的现状简报。用于隔一段时间回到某个课题或项目前。

**开工或接着干之前，重建用户近期的工作上下文，交回一份精炼的现状胶囊：现在做到哪了、下一步该干什么。**

保持精炼、紧扣主题。只读范围内的相关线索，读够就停。

你的上下文活在**两份记录**里。第一份是你自己的聊天记录，记着你做过什么、拍过什么板。第二份是周围的公共记录，记着同一块代码在别的名字下发生的一切：用户反复报的症状、发上去又被撤回的修复、线上还在响的报错——分散在版本库、工单系统、讨论频道、文档和报错追踪里。一个拖得越久的问题，大部分故事越在第二份记录里，所以绝不要只靠翻聊天记录来重建现状。

聊天记录存放在 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`（每行一条消息）。

1. **先分流再动手。** 如果只是接着某一次特定对话继续，走 `session-pickup`；把习惯写成技能卡走 `automate-me`。`recall` 负责跨多段近期对话拉齐开工上下文。如果用户已经给了完整的现状胶囊，直接用，跳过挖掘。
2. **先锁范围再搜索。** 钉死时间窗（“最近”必须变成具体天数，默认近 7 天）、主题（若指定）和工作区（默认当前项目，**未经要求绝不翻别的项目的聊天记录**）。把范围复述回给用户确认。**绝不许悄悄把“全部”缩成“最近几条”。**
3. **并行扫聊天记录。** 用快速便宜的模型派发多个并行子助手分段读取。要求它们按真实修改时间（`ls -t`）排序而不是按 UUID 排序，先按主题检索关键词，只精读命中对话里的相关段落，跳过当前对话和测试噪声。每个助手按统一格式交回发现（主题、目标、决定、未结线索、踩坑与纠正、产出物并附对话 UUID）。原始记录留在子助手里，主对话只留结论。
4. **同步扫公共记录。** 只要主题点名了具体功能、文件、模块或 bug，就默认同步派发调查子助手去查各个外部源（问清现状、试过哪些没站住、用户还在报什么），与扫聊天记录并行跑。没查到结果本身也是发现；若某工具不可用，跳过并如实说明。仅在“我这周干了啥”这类不指明目标的纯活动回顾时跳过此步。
5. **对照实时状态核验。** 把挖出来的 PR、分支和工单用 `git`、`gh` 核对当前真状态。当结论取决于助手当时到底干了什么时，去读完整记录而不是精简副本。
6. **按下面的固定契约写出简报**，按工作线分组，紧扣主题。

## 输出契约（Output contract）

按“概况 → 各线状态 → 反复问题 → 下一步”的顺序写，细节放下面或直接砍掉：

- **概况（Capsule）**：最多 5 条，说清这件事是什么以及整体进展。
- **工作线（Threads）**：每条线一行，行首必须带且只带一个状态标签：`[merged #N]`（已合并）、`[open PR #N]`（PR 还开着）、`[in flight <branch>]`（进行中）、`[verified, uncommitted]`（验证过未提交）、`[reverted #N]`（已撤回）或 `[planned, not started]`（计划未开始）。**没有标签的线就不算整理完，必须贴上标签。**
- **反复问题（Problems）**：最多 5 条，包括用户持续反馈的症状以及发上去又被撤回的修复，**好让下一次尝试从上一次失败的地方开始。**
- **下一步（Next move）**：只给唯一一个最有用的下一步动作，必须具体。

除非阻碍当前主题，否则不扯相邻任务。超出一屏时优先砍细节、不砍工作线。简报需过 **unslop** 去除空话，聊天发现注明 UUID，公共记录注明来源；任何对外输出前清理私密上下文。

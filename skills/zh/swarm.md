# swarm（蜂群并行作业）

> **简介**：派发 N 个并行工作助手分头完成任务，汇总所有结果后返回一份统一报告。用于并行覆盖检查、赛跑、多路探索等场景。

## 启动（Start）

派发任何任务前，先建立按阶段划分的待办清单：
1. Frame（框定任务）
2. Fan out（并行派发）
3. Aggregate（汇总校验）
4. Report（统一汇报）

## 阶段 A：框定任务（Frame）

1. 明确“做完”的判定标准，以及蜂群最终必须返回的产物或报告格式。
2. 选择并行形态：把任务切成独立分片（slices）、让 N 个助手在相同简报上赛跑（race），或两者混合。凡涉及赛跑，启动前必须先宣布选取规则：`first pass`（首个通过）、`rank all`（全部排名）或 `best-of`（择优）。
3. 从 `~/.cursor/rules/pstack-models.mdc` 的 `swarm workers` 行选定工作模型（默认 `claude-opus-5-5-high-fast`）；若是多模型赛跑，事先写明每路使用的模型。按 **poteto-mode** 的子助手规则设置推理强度。
4. 需要写文件时，给每个助手分配独立的可写输出位置。涉及验证或测量特定提交时，简报里写明精确的提交哈希（SHA）；涉及测量时，简报里写明测量方法（样本数、单样本定义、顺序），并要求助手把这两项写进结果里。

## 阶段 B：并行派发（Fan out）

在一条消息里并行启动全部 N 个助手（`subagent_type: generalPurpose`、`environment: "cloud"`、`run_in_background: true`）。只有当助手必须访问用户本地电脑资源时，才改用 `environment: "local"`。需要从非默认远程分支启动时传入 `cloud_base_branch`。

每份简报都必须自包含：写清目标、范围、具体分片或赛跑组别、验证方法以及汇报格式。助手汇报统一使用 `PASS`（通过）、`ISSUES`（有问题）或 `BLOCKED`（受阻）并附证据。能证明缺陷的助手必须报 `ISSUES` 并列出它能证明的所有问题，不能只列第一个。

如果有助手中途退出，继续用剩余的 N-1 份并注明缺口。

## 阶段 C：汇总校验（Aggregate）

读取最终返回结果。如果某份结果没按简报要求写清提交哈希（SHA）和测量方法，直接丢弃并重新派发一次；第二次仍然没写，则记为一个**缺口（gap）——缺口不算通过**。覆盖型任务中，每个必需分片都必须有结果；赛跑型任务则严格执行事先声明的选取规则。不要把助手的原始长篇日志直接糊进总报告。

## 阶段 D：统一汇报（Report）

在对话里返回一份合并后的报告，包含结果总表、逐条精简的问题列表、缺口或中途退出记录，以及赛跑选取规则（如有）。

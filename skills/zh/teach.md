# teach（把人真正讲懂）

> **简介**：用大白话把一块工作讲清楚，让读者真正听懂。底层同时调用 `how` 和 `why` 技能卡，把两者的发现织成一份清晰的讲解。

**你的任务是按对方的节奏，用一份通俗连贯的讲解说清楚：这东西是什么、它怎么运作、以及为什么这样建。目标是让对方真正听懂，而不是去改动任何代码。**

`teach` 架在 `how` 和 `why` 之上。先大致看一眼涉及的范围摸清方位，然后调用 `how` 查运作方式、调用 `why` 查历史动机——这两次都是真正的技能卡调用，让它们各自去挖。把两边的发现融合成一份白话讲解，先讲对方最关心的部分，对方追问时再往深里展开。为了好懂可以自由改写措辞，但有一条绝对例外：**必须原样保留 `why` 里的不确定性措辞（如“可能”“推断”），那些保留字眼本身就是结论，不是文风。**

1. **先想好对方读完该带走哪几件事。** 根据对话里对方提问的目的（准备动手改、做代码评审、排错、刚接触）和已知背景来选，不要反过来盘问对方。对方明显懂的直接跳过，把深度放在对方真正问的地方。
2. **让 `how` 和 `why` 干活，别自己重干一遍。** 自己先扫一遍代码认个路，然后并行跑 `how` 和 `why` 再合并结果。按问题大小决定力度：大模块两个都跑，小改动可能跑一个就够。
3. **从一句大白话定义开始。** 先说出它叫什么、泛指什么（像资深工程师口头聊天那样），再落回眼前具体场景（“在 X 里，我们用它来……”），接着展开怎么运作、深层原因和边界情况。每讲一块，要讲到让人豁然开朗：它解决什么问题、实际怎么跑。遇到人操作触发的流程（比如打开长聊天往上滚），一步步带人走一遍。罗列函数名和常量表是参考手册，不是教学。不要打印装腔作势的标签（比如“最核心的一句话”“TL;DR”）。**先给最小的完整答案——一两句话，而不是密密麻麻一整段——然后停下来**，对方追问再叠下一层，绝不要糊一面字墙。
4. **保持对话感，别搞成宣讲或表演。** 主动提供继续深挖或换下一块的选项，跟着对方节奏走。不要随堂考对方，不要演节奏戏——别打印“暂停”，别叫对方复述，别预告“下面这句很关键”“这里最难”。直接讲就行。该停顿的地方就停下等对方回应。如果是在无真人交互的单次模式里运行，干脆讲完，把“想深挖哪块”放到最后。
5. **能展示就不光靠嘴说，并且一张图一张图地把画面搭起来。** 打开 diff、代码或调试器更快讲懂时就直接展示。画图比文字快时就画图。**凡是超过三个活动部件的东西，绝不要一次画一张全塞满的大图；而是画一组短系列，每张重画上一张并只多加一个部件，让读者看着系统一步步组装起来。** 一次画全、尤其攒到最后才甩出来的图是参考资料，不是教学。具体来说，讲 A → B → C 的流程就画三次：先画 A 到 B，再重画加上 C，再重画加上返回路径。按内容选媒介：流程结构用 Mermaid 图，空间布局/重叠/改前改后用白板手绘风格的简短配图（文字尽量短）。简单到一句话能说清的就不画图。

每一段回复都过一遍 **unslop** 技能卡，用像跟同事聊天一样的平实口语写：紧凑但不生硬，删掉废话和含糊套话，直接讲具体机制。用短句、少用长破折号和堆砌从句；同一个概念从头到尾只用一个名字；避免对称警句和敷衍收尾。上面这些步骤是给你的工作指示，不要把它们抄成标题打印给用户。

**回复要求：** 直接给出讲解本身，绝不要写成“我刚才做了什么”的工作汇报。开门见山抛核心，接着用白话讲清是什么、怎么运作、为什么，最后顺带点出值得用 `how` 或 `why` 继续追查的线索。
